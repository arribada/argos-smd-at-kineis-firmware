# CRITICAL (1)
### [CRITICAL] mgr_err.c — concurrency-isr @ mgr_err.c:219-227 (EXTI line config + STOP2 entry)
checkCrashLoop's STOP2 safe-sleep configures the WRONG EXTI line for the RTC wakeup timer AND never enables the PWR internal wake-up line. On STM32WL55 the RTC Wakeup Timer is EXTI line 20 (RTC_EXTI_LINE_WAKEUPTIMER_EVENT == EXTI_IMR1_IM20, stm32wlxx_hal_rtc_ex.h:1231; RM0453 line 15589-15590: 'To wake up from Stop mode with an RTC wake-up event ... Configure the EXTI line 20 to be sensitive to rising edge'). This code instead sets EXTI_IMR1_IM17 / RTSR1 bit17 / FTSR1 bit17 — line 17 is the RTC *Alarm* line (RTC_EXTI_LINE_ALARM_EVENT == EXTI_IMR1_IM17, stm32wlxx_hal_rtc.h:837), a different event. The wakeup-timer EXTI (line 20) is left masked. Additionally, unlike the proven STOP2 path in mgr_lpm_uw.c:931-935 which calls HAL_PWREx_EnableInternalWakeUpLine() with the explicit comment 'Without this RTC fires its IRQ but the chip doesn't exit STOP2', this function never enables the internal wake-up line at all.

- **Impact:** When a crash loop is detected (>=10 consecutive short boots), the chip enters STOP2 with no valid wake path: the RTC WUTF fires but neither the correct EXTI line (20) nor the PWR internal wake-up line is armed, so the core does not exit STOP2. On a sealed UW_DOPPLER unit this is a permanent BRICK — the very crash-loop protection meant to preserve battery instead strands the device forever (IWDG is frozen in STOP2, magnet/reed is not configured as a wake here). Exactly the failure class the deployment must never hit.
- **Fix:** Do not hand-roll the EXTI/PWR wake plumbing. Mirror the validated mgr_lpm_uw.c STOP2 entry: use HAL_RTCEx_SetWakeUpTimer_IT(&hrtc, CRASH_LOOP_SLEEP_S-1, RTC_WAKEUPCLOCK_CK_SPRE_16BITS, 0) (handles WPR unlock, WUTWF poll, and the correct EXTI line internally) and call HAL_PWREx_EnableInternalWakeUpLine() before HAL_PWREx_EnterSTOP2Mode. If the manual register approach is kept, change IM17->IM20 (EXTI->IMR1 |= EXTI_IMR1_IM20; RTSR1/FTSR1 bit 20) and add the internal wake-up line enable. Add a unit/bench test that proves wake actually occurs. Also add an RTC-liveness gate (HAL_RTC_WaitForSynchro) before entry, matching the LSE-death guard already added elsewhere — otherwise a dead crystal here is also a strand.

# HIGH (42)
### [HIGH] bl_crc.c — robustness @ Bootloader/Src/bl_crc.c:97-110
bl_crc32_flash validates only start_addr against [0x08000000, 0x08040000) but never bounds start_addr + length_bytes. A large length_bytes (or start near the top of flash) makes bl_crc32_calculate read past 0x08040000 (end of flash) into reserved/option/peripheral address space. There is also an unchecked uint32 overflow: start_addr + length_bytes can wrap. The function is a public API and carries no caller-side guarantee.

- **Impact:** Over-read past flash end during app integrity verification. In the sealed deployment this is reached via bl_validate_app_crc(header) with header->app_size taken from the on-flash app header. The only thing preventing the over-read today is that bl_validate_app_header() caps app_size<=APP_MAX_SIZE and pins app_start_addr==APP_FLASH_BASE BEFORE the CRC is computed — but that ordering lives in the caller, not here. If a corrupt/garbage header is ever CRC-checked without that prior cap (e.g. a future caller, or header validation reordered), the bus access past flash end can fault/hang the bootloader, which on a sealed unit means no recovery.
- **Fix:** Add an end-bound + overflow check inside bl_crc32_flash: reject if length_bytes > (0x08040000 - start_addr), i.e. compute the remaining span as a uint32 and compare, before casting start_addr to a pointer. Return 0 on violation as the existing range failure does.

### [HIGH] bl_crc.c — bug @ Bootloader/Src/bl_crc.c:77-90 (contract) vs Bootloader/Src/bl_dfu.c:228-262 and bl_main.c:730
CRC accumulate/verify domain mismatch. In bl_dfu_cmd_write, flash is written with 0xFF-padded data (aligned_len, bl_dfu.c:233-246) but the running CRC is accumulated over only the unpadded payload: bl_crc32_accumulate(payload, payload_len) (bl_dfu.c:262). The final image is then re-CRC'd over the whole padded flash span via bl_crc32_flash(app_start, app_size) in bl_validate_app_crc (bl_main.c:730). If any WRITE chunk has payload_len not a multiple of 8, the accumulated DFU CRC (over unpadded bytes) and the flash CRC (over padded bytes, including injected 0xFF) cover different byte streams and will not match the same expected value. The two CRC consumers (DFU VERIFY at bl_dfu.c:315 vs boot-time validate at bl_main.c:730) therefore disagree on what 'the CRC' is.

- **Impact:** For aligned/full chunks (the normal host case) both agree, so this can pass all bench tests and still be a latent integrity hole: a tool that sends a final short unpadded chunk produces a flash image whose boot-time CRC differs from the DFU-accepted CRC. Worst case a unit accepts a DFU that the boot validator later rejects (boot loop) or vice-versa. On a sealed unit this is a brick risk.
- **Fix:** Make the accumulated CRC cover exactly the bytes written to flash: accumulate aligned_data over aligned_len (matching bl_flash_write), so the running CRC equals bl_crc32_flash over the same padded span. Add a unit test asserting accumulate-over-padded == flash-CRC for a non-8-aligned final chunk.

### [HIGH] bl_dfu.c — robustness @ bl_dfu.c:267-296 (bl_dfu_cmd_read); reachable via bl_main.c:403-422 UART 'AT+DFU=READ' and bl_main.c:484-495 SPI READ_REQ
READ command performs NO session check and NO app-region restriction. It memcpy's directly from any address within the whole 256 KB flash window (bl_flash_read only validates address>=FLASH_BASE and end<=FLASH_BASE+256KB, see bl_flash.c:199-224). The Kineis credentials (ID/ADDR/SECKEY) live at FLASH_USER 0x0803B000 and the credential mirror at FLASH_PMLOG 0x08032800 - both inside that window and both readable via DFU READ.

- **Impact:** A host with serial/SPI access to a bootloader-mode device can dump the Kineis secret key and radio credentials, and the entire bootloader image, with no DFU session required. For a sealed unit this is only reachable after AT+BOOT, but it is an unrestricted secret-exfiltration primitive that the WRITE path (which is app-region-bounded) deliberately avoids.
- **Fix:** Restrict READ to the application region: reject if !bl_flash_addr_in_app(address) || !bl_flash_addr_in_app(address+read_len-1). If READ is only meant for write-back verification, that range is sufficient; never expose FLASH_USER / FLASH_PMLOG / bootloader.

### [HIGH] bl_main.c — robustness @ bl_main.c:589-599 (bl_state_error) reachable from 184-187 (JUMP_APP) via 227-234 (CHECK_APP)
bl_state_error() unconditionally routes to BL_STATE_DFU_UART when detected_protocol != BL_PROTO_SPI, including when detected_protocol == BL_PROTO_NONE. That NONE case is reachable: cold boot with NO DFU flag -> bl_state_init -> BL_STATE_CHECK_APP -> bl_check_app_valid()==true -> BL_STATE_JUMP_APP -> bl_jump_to_app(). If the jump's own SP/entry validation (617-624) fails and returns (it uses a DIFFERENT, stricter check than bl_check_app_valid: bl_check_app_valid reads SP/entry from the HEADER's app_start_addr-derived fallback only when header invalid, while jump reads SP/entry from header->app_start_addr when header magic is valid — the two can disagree), line 186 sets current_state=BL_STATE_ERROR with detected_protocol still BL_PROTO_NONE. bl_state_error then sets BL_STATE_DFU_UART, but neither bl_uart_init() nor bl_uart_start_rx() was ever called on this path (no DETECT_PROTOCOL was run). bl_state_dfu_uart() then calls bl_uart_process() on an uninitialized UART.

- **Impact:** On a unit whose app header is present/valid but whose vector-table SP/entry words fail jump validation, the bootloader lands in a UART-DFU state with the UART peripheral never initialized — it will not service AT+DFU= commands and provides no recovery, i.e. an effectively bricked unit with no field input (sealed). Low probability but a genuine no-recovery hang path.
- **Fix:** In bl_state_error(), when detected_protocol == BL_PROTO_NONE, run protocol detection (set state to BL_STATE_DETECT_PROTOCOL) instead of jumping straight to DFU_UART; or have bl_state_error() lazily call bl_uart_init()/bl_uart_start_rx() before entering DFU_UART. Also make bl_check_app_valid() and bl_jump_to_app() share one validation routine so they cannot disagree.

### [HIGH] bl_spi.c — bug @ bl_spi.c:443-448, 485-487
When a valid A+ frame carries data_len in 249..255 (uint8_t LEN allows up to 255, but payload_buffer is BL_CHUNK_SIZE=248), the guard `if (payload_len > 0 && payload_len <= BL_CHUNK_SIZE)` SKIPS the memcpy into payload_buffer, yet payload_len is still set to the oversized value (line 444 `payload_len = request->data_len`). cmd_ready becomes true. The non-WRITE_DATA branch of bl_spi_get_payload (line 485) then does `len = (payload_len < max_len) ? payload_len : max_len; memcpy(buffer, payload_buffer, len)` and copies up to 248 bytes of STALE payload_buffer contents (leftover from a previous command) to the caller as if it were this command's payload. No error is returned; the bootloader silently acts on stale data.

- **Impact:** A malformed/oversized SPI frame (or a host bug producing LEN 249..255) makes a DFU command operate on stale payload bytes instead of being rejected. For SET_HEADER / VERIFY / ERASE-with-args this can write a wrong app header or wrong CRC/address into flash silently. On a sealed unit the bootloader is the only field-recovery path, so a corrupt update that still reports OK is a brick risk.
- **Fix:** Reject the frame when payload_len > BL_CHUNK_SIZE: send DFU_RSP_SIZE_ERROR (or BL_PROT error), call bl_spi_start_rx() and return false, instead of proceeding with cmd_ready=true. Do not leave payload_len set when the copy was skipped.

### [HIGH] app_header.c — build-config @ Core/Src/app_header.c:91-97 (and comments :9,:50-56,:89,:95-97,:100-102)
The header is shipped with permanent placeholder values: app_size=0xFFFFFFFF (:91), app_entry_point=0xFFFFFFFF (:92), app_crc32=0xFFFFFFFF (:96), header_crc32=0xFFFFFFFF (:97). The file comments repeatedly claim these are 'filled by create_dfu.py'. They are NOT. Tools/create_dfu.py (the only DFU tool the Makefile invokes, Makefile:722) merely extracts the binary, prints a CRC, and discards it (create_dfu.py:111-127) -- it never patches the .app_header bytes. No post-link patch step exists in the Makefile (verified: only -j .app_header at Makefile:702, no objcopy --update-section, no separate patcher). The only code that builds a real header is Tools/dfu_tool.py:create_app_header (dfu_tool.py:262-294), a separate manual host tool that fabricates its OWN 256-byte header and prepends it to a raw .bin -- it never modifies the compiled application_header struct. So the struct ships exactly as written here.

- **Impact:** The bootloader's strong validation path is permanently dead in production. bl_validate_app_header (Bootloader/Src/bl_main.c:713) rejects the shipped header because app_size==0xFFFFFFFF > APP_MAX_SIZE, so bl_validate_app_crc (bl_main.c:730, which CRC-checks the whole app image against app_crc32) is never reached. bl_check_app_valid silently falls back to the legacy vector-table-only sanity check (bl_main.c:680-692). Net for the sealed deployment: the promised app-image integrity check (catch a corrupted/partial DFU before jumping) NEVER runs. A truncated or bit-rotted app that still has a plausible SP/PC at 0x08000000 will be jumped into. Not an immediate brick, but it removes the anti-brick guarantee the header was built to provide.
- **Fix:** Either (a) wire a real post-link patch into the Makefile .bin/.hex/dfu recipe (objcopy --update-section .app_header=patched, computing app_size + CRC-32/MPEG-2 over the app image and writing header_crc32), OR (b) if the header is intentionally decorative and the BL legacy fallback is the real boot gate, delete the false 'filled by create_dfu.py' comments and document that app_size/app_crc32 are unused so no one trusts a non-existent integrity check. Do not leave the comments asserting a guarantee the build does not deliver.

### [HIGH] gpio.c — concurrency-isr @ Core/Src/gpio.c:167-174 vs Kineis/Extdep/Mcu/Src/mcu_misc.c:106-111
On SMD_STDALONE, MX_GPIO_Init() unconditionally configures PC1 (PA_PSU_SEL = TPS63901 VSEL) as OUTPUT_PP and drives it HIGH (lines 168/174). This is INTENTIONAL at boot (matches main.c:733-745 which drives PC1 HIGH bare-metal pre-clock for 3V3-mode robustness), but MX_GPIO_Init is ALSO re-invoked on every STOP2 wake (mgr_lpm_uw.c:1067). mcu_misc.c:106-111 documents the opposite rule: 'on STDALONE leave PC1 high-Z, driving it re-programs the buck-boost output while PA pulls inrush = guaranteed brownout.' The two are reconciled only by sequencing (VSEL is re-driven HIGH=3V3 at wake, PA inrush happens later via MCU_MISC_turn_on_pa which does NOT touch SEL on STDALONE). The risk: any future wake path that calls MX_GPIO_Init while VSEL was deliberately set LOW (1V8 power-save via MCU_MISC_VSEL_set(false)) will silently snap it back to 3V3, defeating the power-save and momentarily glitching VSYS. mgr_lpm_uw.c relies on this exact 're-drive HIGH on wake' behavior (comment at mgr_lpm_uw.c:160), so it is currently load-bearing and correct — but it is an implicit, undocumented coupling on a brownout-sensitive pin.

- **Impact:** Sealed deployment: if any code drops VSEL to 1V8 and then a wake/re-init runs MX_GPIO_Init, VSEL is forced back to 3V3 with no log — power-save silently lost. Worse, the runtime drive itself is a glitch source on the TPS63901 feedback node; the codebase elsewhere treats driving SEL as a brownout hazard. The behavior is only safe because of an undocumented call-ordering invariant.
- **Fix:** Document the invariant explicitly at gpio.c:167 ('PC1 is re-driven HIGH on every wake by design; any 1V8 power-save MUST be re-applied AFTER MX_GPIO_Init, never before'). Consider gating the PC1 drive in MX_GPIO_Init behind a 'first boot' check, or centralizing VSEL ownership in MCU_MISC_VSEL_* so gpio.c does not silently override it.

### [HIGH] main.c — bug @ Core/Src/main.c:877-879 (and the stale re-read at 893)
The cold-boot vs fault-reset gate that decides whether to run Sram2_Init() reads the LIVE RCC->CSR ('uint32_t csr = RCC->CSR;' at 877, 'boot_rcc_csr = RCC->CSR;' at 893). But __HAL_RCC_CLEAR_RESET_FLAGS() at line 753 already wiped CSR (sets RMVF) whenever PINRSTF was set. Per RM0453 §RCC_CSR (p.341, bit 26): on STM32WL an internal reset (IWDG/SFT/BOR/WWDG) also drives the bidirectional NRST line, so PINRSTF is set alongside IWDGRSTF/SFTRSTF on essentially every reset. The PINRST branch (752-755) therefore fires and clears the flags before line 877 reads them — so '!(csr & (RCC_CSR_IWDGRSTF | RCC_CSR_SFTRSTF))' evaluates TRUE on an IWDG/software reset, and Sram2_Init() runs. The correct, pre-clear value was already captured into g_boot_rcc_csr_raw at line 712 but is not used here.

- **Impact:** On a watchdog (IWDG) or software reset (MGR_ERR_logAndReset / Error_Handler / fault-handler NVIC_SystemReset) in the sealed UW_DOPPLER unit, Sram2_Init() wrongly re-initialises the .data2/.bss2 RAM2 sections — wiping the forensic event log (mgr_evtlog .retentionRamBss), TX stats (mgr_txstats/mgr_rate) and other .retentionRamData/.retentionRamBss that were deliberately placed in retention RAM to SURVIVE these exact reset classes. Directly defeats the retention design described in the same comment (872-879) and in the linker (.bss2/.data2 vs .retention_noload). Crash-loop counter itself survives (it is in NOLOAD) but post-mortem forensics on a fielded brick are lost.
- **Fix:** Use the preserved pre-clear value, not the live register: 'if (!(g_boot_rcc_csr_raw & (RCC_CSR_IWDGRSTF | RCC_CSR_SFTRSTF))) Sram2_Init();' at 878, and replace the line-893 'boot_rcc_csr = RCC->CSR;' with g_boot_rcc_csr_raw (it is only used for logging anyway). Add a unit test mirroring the decision table (IWDG/SFT/BOR/PIN/cold -> Sram2_Init yes/no).

### [HIGH] rtc.c — hw-config @ Core/Src/rtc.c:133-134 (HAL_RTC_MspInit) interacting with Drivers/.../stm32wlxx_hal_rcc_ex.c:149-160
On a wake from SHUTDOWN/STANDBY where the LSE crystal was alive at the previous boot but is now dead, g_rtc_use_lsi=1 so MspInit requests RTCCLKSOURCE_LSI while the backup-domain BDCR still has RTCSEL=LSE (it survives shutdown). HAL_RCCEx_PeriphCLKConfig detects current(LSE) != requested(LSI) and performs __HAL_RCC_BACKUPRESET_FORCE()/RELEASE(), which wipes the ENTIRE backup domain: the RTC calendar/counter AND the RTC backup registers that hold the LPM mode (lpm_ctxt in .lpmSection, see main.c:771-772) and the MGR_ERR/TAMP forensic state. This MspInit runs at main.c:812, i.e. AFTER LPM_getMode() was read once (main.c:854) but BEFORE the second LPM_getMode() at main.c:1059 and before any code that relies on the backup-register LPM context. A wiped BKPR makes the second LPM_getMode() return NONE, so the wake-from-shutdown RTC_WKUP_IRQHandler simulation (main.c:1070) is skipped and timed-wake bookkeeping is lost. On the sealed unit this degrades a marginal-LSE recovery boot rather than recovering cleanly.

- **Impact:** Sealed-deploy degraded-LSE recovery path: the backup-domain reset silently destroys the LPM-mode context and RTC time exactly in the LSE-death scenario the LSI fallback exists to survive. Wake-cause dispatch and any RTC-time continuity is lost on that boot. Low probability (needs LSE alive-then-dead across a shutdown) but high impact because it is the corner the fallback is meant to harden.
- **Fix:** On the wake-from-shutdown branch (rtc.c:35-66) the RTC is already configured; do not call the full HAL_RCCEx_PeriphCLKConfig clock-source reselect via HAL_RTC_MspInit when the source would change. Either (a) read RTCSEL from BDCR and skip the PeriphCLKConfig if it already matches, or (b) gate the RTCClockSelection switch so a backup-domain reset is never triggered on a wake path — only on the NONE/cold path. Confirm with a bench test: boot on LSE, force g_rtc_use_lsi at wake, verify lpm_ctxt/RTC counter survive.

### [HIGH] spi.c — hw-config @ Core/Src/spi.c:86-98 (MspInit), in combination with Makefile/kns_app_uw_doppler.c:92-96
On SMD_STDALONE the SPI1 AF pins collide with load-bearing GPIO: PA1=LED_RED, PB4=LED_GREEN, PB5=LED_BLUE, and the adjacent PB6=REED / PB7=PWR_LATCH (per gpio.c:93,129-130 and BSP_LED_wiring memory). MspInit forces PA1/PB4/PB5 to AF5_SPI1 push-pull. The UW_DOPPLER #error guard (kns_app_uw_doppler.c:92-96) only checks BSP feature macros, NOT the COMM choice, so `APP=UW_DOPPLER BOARD=SMD_STDALONE COMM=SPI` is a fully buildable configuration. - **Impact:** A mis-specified sealed build (SPI instead of UART) would silently repurpose the deploy-status LEDs as the SPI bus. No compile-time guard catches it. While the documented sealed target is UART (so not the default), there is no defense-in-depth: one wrong COMM= flag produces a board where the field-diagnostic LEDs and SPI are wired to the same pins. Given the 'never brick a sealed unit' bar this is a latent landmine.
- **Fix:** Add a compile-time guard (e.g. in kns_app_uw_doppler.c or a board header) that errors on `USE_SPI_DRIVER && SMD_STDALONE` (or more precisely USE_SPI_DRIVER together with BSP_HAS_LED_RGB on the same pads), mirroring the existing UW_DOPPLER #error pattern. ### [HIGH] subghz.c — concurrency-isr @ Core/Src/subghz.c:115
Hardcoded NVIC enable targets the WRONG interrupt. `NVIC->ISER[1] = (1UL << 12)` sets bit 12 of ISER[1], i.e. IRQ 32+12 = IRQ 44 = SUBGHZSPI_IRQn — NOT the radio IRQ. On the CM4 core SUBGHZ_Radio_IRQn = 50 (stm32wl55xx.h:165), which would need ISER[1] bit 18 ((1UL<<18)). The intended radio IRQ is in fact still enabled correctly via HAL_NVIC_EnableIRQ(SUBGHZ_Radio_IRQn) at line 112 and via HAL_SUBGHZ_MspInit (line 134), so the radio works DESPITE this line — making the line both useless for its stated purpose and a latent landmine.

### [HIGH] tim.c — bug @ Core/Src/tim.c:41 (Prescaler=31999) vs Kineis/Extdep/Mcu/Src/mcu_tim.c:258,303
Prescaler 31999 yields a 1 ms tick, but the consumer mcu_tim.c documents and codes a 500 us step. TIM16 is on APB2; with HSI16/PLLM4*PLLN32/PLLR4 = SYSCLK 32 MHz (main.c:1153-1157), APB2CLKDivider=DIV1 (main.c:1172), the APB2 timer clock is 32 MHz (no x2 because APB prescaler is /1). 32 MHz / (31999+1) = 1000 Hz = 1 ms per count. mcu_tim.c MCU_TIM_start computes cnt_val = timeout_ms*2-1 (mcu_tim.c:258) and MCU_TIM_getCount divides the counter by 2 (mcu_tim.c:303), both of which only hold if one count = 500 us. With a 1 ms tick the actual TX-timeout period is ~2x the requested timeout_ms, and getCount reports ~half the real elapsed time.

- **Impact:** MAC TX-timeout safety timer fires at roughly double its intended duration. In the sealed UW_DOPPLER deployment a stuck/aborted TX is detected late, lengthening RF-on time and wasting battery; in the worst case the MAC's own watchdog/IWDG assumptions about timeout granularity are violated. Also halves the ARR headroom: at the assumed 500 us step the 16-bit ARR limit is ~32.7 s of timeout, but at the real 1 ms step the same cnt_val overflows checks are mis-scaled.
- **Fix:** Confirm the intended tick with the Kineis MAC spec. If 500 us is required, set Prescaler=15999 (32 MHz/16000 = 2 kHz = 500 us). If 1 ms is intended, fix mcu_tim.c to stop multiplying/dividing by 2. Do not change one side without the other — add a _Static_assert or a comment tying tim.c prescaler to the mcu_tim.c step assumption.

### [HIGH] kns_cs.c — concurrency-isr @ Kineis/Extdep/Conf/kns_cs.c:38-39,46-48,53-56

- **Impact:** In the sealed UW_DOPPLER deployment, MAC ISR activity concurrent with main-loop queue access can corrupt the save stack, causing IRQs to be re-enabled while a critical section is still nominally held (silent data race on queue indices) or left disabled. - **Fix:** Treat as vendor boundary but harden the call sites: ensure KNS_CS is only entered with IRQs already masked from the same context, or replace with the proven save/restore idiom used elsewhere (uint32_t prim = __get_PRIMASK(); __disable_irq(); ... __set_PRIMASK(prim);) which needs no shared counter. ### [HIGH] mcu_flash.c — concurrency-isr @ mcu_flash.c:282-328 (increment_wear_counter overflow branch)
The WL-full overflow branch first calls MCU_FLASH_write(of_addr,...) - **Fix:** Document the non-atomicity explicitly and accept the forward-only skew, OR reorder so the WL-area erase/reset completes before the overflow word is bumped (overflow word is the authoritative high digit; bumping it last keeps monotonicity).
